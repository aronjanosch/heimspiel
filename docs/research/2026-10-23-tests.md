## 1. Quiver Launcher 3.5.1 (AppImage)

**Setup.** AppImage copied into an empty folder. On first start Quiver creates `settings.json`, `Apps/` and
`Cache/` next to it, but `apps.json` only once something is added. `--list` shows only the local library,
not the catalog: "ERROR: No games found in library." (rc 1).

**Entries without the GUI.** `apps.json` is documented (`apps.json.example`, `docs/single-app-add.md`) and
read by `Services/AppCatalogService.cs:248-337`. A hand-written entry is enough:

```json
{ "apps": [
  { "name": "Zelda64Recomp", "repository": "Zelda64Recomp/Zelda64Recomp",
    "folderName": "Zelda64Recomp", "releaseAssetFilter": "Linux-X64.zip" },
  { "name": "Zelda64RecompWin", "repository": "Zelda64Recomp/Zelda64Recomp",
    "folderName": "Zelda64RecompWin", "releaseAssetFilter": "Windows.zip", "linuxRunner": "proton" }
] }
```

Without `*`/`?`, `releaseAssetFilter` matches as a substring, otherwise as a glob
(`lib/QuiverLauncher.Core/Services/RepositorySourceHelper.cs:91-102`). Other fields: `repositorySource`
(github/gitlab/codeberg), `installPath`, `preferredVersion`, `autoUpdate`, `linuxRunner` (wine|proton),
`linuxPrefixPath`, `linuxProtonPath`, `linuxCustomLaunchCommand`, `filesToAdd`, `tags`.

**`--download`.** Downloads and extracts in 3 s into `Apps/<folderName>/` (executable, `version.txt`,
`installed-build.txt` with the asset's SHA-256). **The process then never exits**: reproduced four times,
also with stdin `/dev/null` and under a pseudo-TTY (`script`), once for more than 10 min. The progress loop
is left; what hangs is `await downloadTask` or the status check after it (`Services/CLIHandler.cs:675-677`).
We did not capture the managed stack (`dotnet-stack` needs a .NET SDK). `--uninstall` exits normally (rc 0).

**`--run` with the Linux build.** `--run Zelda64Recomp` starts the game (SDL, Wayland) and blocks. After the
window was closed by hand, Quiver exited too. According to the code it waits for the process and then for
its process group (`Services/CLIHandler.cs:484-525`).

**`--run` with the Windows build via Proton.** Without further settings Quiver picks the first Proton it finds
(`~/.steam/root/steamapps/common/Proton - Experimental`), creates the prefix in
`Apps/<folder>/.steam-compat-data` (436 MB including the prefix) and launches via
`proton waitforexitandrun`. The window runs under XWayland with class `steam_app_<id>`. When the game is
terminated (SIGTERM to `Zelda64Recompiled.exe`), Quiver returns after 1 s and `wineserver` is gone. Steam was
running at the time; launching without a running Steam client is untested.

**Side finding.** On the Proton launch Quiver wrote `linuxRunner`, `linuxProtonPath` and `linuxPrefixPath`
into the *Linux* entry (same repository); the Windows entry stayed empty. Two entries for the same repo get
mixed up.

**Design conclusions.**
- The decision "Quiver as a dependency" stands: `--run` works as a blocking launch command for ES-DE, including
  Windows builds via Proton.
- heimspiel writes Quiver entries into `apps.json` itself, and only while Quiver is not running. Write
  atomically like Quiver does (temp file + rename) and respect the backups in `Backups/apps`. One entry per
  repo; `releaseAssetFilter` picks the build.
- Do not wait blindly on `--download`: call it with a timeout, detect completion via `installed-build.txt` or
  `--list` → `[INSTALLED]`, then end the process. The automatic update inside `--run`
  (`CLIHandler.cs:362-370`) carries the same risk, so either call `--update` with a timeout before launching
  or disable updates for ES-DE launches. Report upstream (see the item "Upstream-PR an Quiver").
- Never control windows through compositor tools (`hyprctl`, `kdotool` …): heimspiel must treat Hyprland, KDE
  and GNOME alike, and `hyprctl dispatch` already changed with 0.56 (Lua syntax). Use processes and process
  groups only.

## 2. ES-DE 3.5.0 on Hyprland: return and focus

**Setup.** `ES-DE_x64.AppImage --home <scratch>/esde-home --create-system-dirs` creates 191 system folders;
`ROMDirectory` is preset in `es_settings.xml`. The five Steam `.desktop` files from
`~/.local/share/applications` (`Exec=steam steam://rungameid/<id>`) sit unchanged in `ROMs/steam/`.
In `ROMs/ports/` a shell script runs `quiver --run Zelda64Recomp`.

**Heroic 2.22.4 (AppImage, x86_64), fresh install, logged in to Epic, GOG and Amazon.**
- The shortcut settings are **off by default**: `addDesktopShortcuts`, `addStartMenuShortcuts` and
  `addSteamShortcuts` are all `false`.
- They live in `~/.config/heroic/config.json` under `defaultSettings` and are mirrored in
  `~/.config/heroic/store/config.json` under `settings`. The `store/configStore.json` path assumed in the
  research does not exist.
- Default install path: `defaultSettings.defaultInstallPath` = `~/Games/Heroic`.
- Conclusion: with default settings Heroic creates no `.desktop` files, so ES-DE's Game Importer finds nothing.
  Turning the setting on would only affect future installs. heimspiel therefore reads the installed games
  itself (`installed.json` of legendary, gog_store and nile) and writes the `.desktop` files. Setting
  `addStartMenuShortcuts` is optional at most.
- An unintegrated Heroic AppImage registers no `heroic://` handler (`xdg-mime query default
  x-scheme-handler/heroic` is empty), so Heroic's own `.desktop` files (`xdg-open heroic://…`) would not
  launch anything. The test entry calls the AppImage directly:
  `Exec="<…>/Heroic.AppImage" --no-gui "heroic://launch?appName=<id>&runner=gog"`. heimspiel must detect how
  Heroic is installed (AppImage, Flatpak, AUR) and write the matching command.

**Steam on Hyprland (2026-10-24).** ES-DE starts fullscreen (log: `Screen mode: fullscreen`, 3840x2160 at
240 Hz, display 1). Into the Breach (launched three times) starts fullscreen. **After the game exits, ES-DE comes
back as a tiled window, not fullscreen.** Hyprland allows one fullscreen window per workspace; the game takes it,
Hyprland does not give it back, and ES-DE (still running because of `%RUNINBACKGROUND%`) does not request it
again.

ES-DE's window: class `es-de`, title `ES-DE`, runs under **XWayland**, `fullscreen = 2`. Workaround tested: a
Hyprland Lua handler on `window.destroy` that sets ES-DE back to fullscreen
(`hl.dsp.window.fullscreen({ window = "address:…", action = "set", mode = "fullscreen" })`) unless another
window on its workspace is fullscreen. A static window rule does not help, because it only applies on map.
With the handler, ES-DE came back fullscreen after Into the Breach and Slay the Spire 2. API references:
hyprland-wiki `content/configuring/core/dispatchers.md` (`fullscreen`, `fullscreen_state`) and
`advanced-configuration/events.md` (`window.destroy`). Conclusion: the setup wizard offers this handler as an
opt-in snippet on Hyprland, in its own file that is only `require`d after asking. heimspiel itself still
never controls windows. KDE/GNOME still to check.

**gamescope** (3.16.31 installed) is not a way out for Steam/Heroic. `steam steam://rungameid/…` and a
running Heroic hand the launch to their already running client, so the game would open outside the gamescope
window. Untested so far; reasoning only.

**`game-start` hook arguments (2026-10-24).** For `.desktop` entries ES-DE passes the expanded `Exec` command as
the first argument, not the file path: `steam steam://rungameid/590380 | Into the Breach | steam | Valve Steam`.
The hook runs for every game in every system. RomM-ES's `GameStart.py:54` then crashes with
`FileNotFoundError` (ES-DE launches the game anyway), and every launch pays for the hook's start-up time.
The arguments are not reliable either (see test 3): for Heroic's quoted `Exec` they arrived as
`<AppImage> | --no-gui | heroic://… | Beat Cop` (no system at all); file paths arrive shell-escaped
(`Legend\ of\ Zelda,\ The…`). Conclusion: heimspiel's hook unescapes argument 1, checks whether it is one of
its own placeholders, and exits immediately otherwise. It never relies on argument positions. This corrects the
research ("arguments: ROM path, name, system, system name").

**Heroic and Quiver through ES-DE (2026-10-24, with the handler active).**
- Beat Cop (GOG via Heroic, Windows build via GE-Proton) launches from the `epic` system with
  `"<…>/Heroic.AppImage" --no-gui "heroic://launch?appName=1584866499&runner=gog"`. No Heroic process remained
  afterwards.
- Zelda64Recomp (Quiver) launches from `ports` (`/usr/bin/bash <…>/Zelda64Recomp (Quiver).sh` →
  `quiver --run`; no error, no update).
- In all cases (Steam, Heroic, Quiver) the user reported: game starts, ES-DE comes back fullscreen and can be
  used right away. Everything stayed on the same monitor (display 1, 3840x2160).

**Conclusion for test 2.** The decision "ES-DE, no fork" stands. On Hyprland, returning to fullscreen needs
the opt-in handler above. Focus and monitor need no extra work. Still to check: KDE and GNOME.

## 3. RomM-ES against our own RomM server

**Setup.** RomM-ES (commit of 2026-10-23) runs with `mise x uv -- uv run --with requests==2.28.2 python -I`.
`settings.ini` (0600) is prefilled except for URL/token: `import_all_platforms = false`, no videos or
manuals. The `game-start` hook is our own wrapper script with correct quoting (the bundled `GameStart.sh:12`
quotes incorrectly); `CustomEventScripts` is on. `n64`, `snes` and `gba` are redirected via `custom_systems`
to a fake emulator that logs size and SHA-1 of the file it receives. This lets us check the hook without an
installed emulator.

**Correction to the research.** In `GameStart.py:148-150` the token is logged only at debug level (default is
INFO). It is, however, part of the curl command line and therefore visible in `ps`.

**Import (2026-10-24, RomM on the LAN, platform `n64`, 305 games, media limited to covers and screenshots).**
- The first two runs aborted after ~13 s with `Temporary failure in name resolution`. RomM-ES calls
  `requests.get` per image without a session (`GameImporter.py:247`), ~28 requests/s with a new connection each.
  The LAN DNS server then answered **REFUSED for every name** on this host for 103 s (rate limit).
  RomM-ES has no retries, so the whole import stops.
- After an aborted run the 195 placeholders and 362 images remain, but `gamelist.xml` is empty
  (`<gameList></gameList>`): the gamelist is written only at the end.
- A second run creates no duplicates (still 195 placeholders, 362 images), so placeholders and media are idempotent.
- With a wrapper that routes `requests.get` through one keep-alive session at 5 requests/s (RomM-ES itself
  unchanged), the import finished in 1:53 min: 305 placeholders, 559 images, 305 `<game>` entries. DNS stayed fine.
- Placeholder: 12-byte file `RomM-ES:3037` named like the RomM file (`… Majora's Mask (USA).n64`). Gamelist entry
  with name, release date, rating, publisher, developer, players, genre, description; cover and screenshot named
  after the file stem. ES-DE shows the games with covers.
- RomM-ES also imports non-ROM files from RomM (save files `Mario Kart 64 (U) [!].eep`/`.mpk`); ES-DE skips them
  with a warning ("extension is not configured").

**Launch hook.** Launching Majora's Mask in ES-DE: the hook downloaded the 32 MiB ROM in about 1 s and replaced
the placeholder in place; the fake emulator then received the real file (SHA-1 `22f8bfa1…`). The user noticed only
a short stall. ES-DE shows nothing while the hook runs. The download is permanent (no cache, no clean-up).
Triggering the hook by hand with ES-DE's arguments works the same way (Ocarina of Time, SHA-1 `3ac86253…`).

**Design conclusions.**
- The concept (placeholder + blocking `game-start` hook that swaps in the real file) works with ES-DE 3.5.
- heimspiel's RomM client: one HTTP client with keep-alive (`romm-api`/reqwest does this), a request limit for
  media, retries with backoff, timeouts.
- Write `gamelist.xml` atomically, also after partial failures, so placeholders never exist without metadata.
- Import only files whose extension the ES-DE system accepts.
- Large files (PS2/GC images) will block ES-DE for minutes without feedback. Options: pre-download from the
  setup/desktop view, or a progress window started by the hook. To be decided in the RomM item.
- Keep the downloaded files in a size-limited cache (symlink into the ROM folder) instead of replacing the
  placeholder for good.

## 4. librecomp: pre-placed ROM

**Code** (N64ModernRuntime `librecomp/src/recomp.cpp`, state of 2026-10-23):
- Stored as `config_path/<game_id>.z64` (lines 63-64). Linux: `~/.config/Zelda64Recompiled/` (created on the
  first start of Zelda64Recomp); `game_id` Zelda64Recomp = `mm.n64.us.1.0`, BanjoRecomp = `bk.n64.us.1.0`.
- At startup `check_all_stored_roms()` checks with **XXH3-64** against `rom_hash` (lines 164-167, 197-221):
  MM US `0xEF18B4A9E2386169`, BK US `0x1B67585D56E07F8C` (each in `src/main/main.cpp`).
- Wrong hash → the file is **deleted** (lines 202, 234).
- Byteswapping (`.v64`/`.n64` → big-endian) happens only in the dialog path `select_rom()` (lines 378-390), not
  when loading the stored file. heimspiel must convert to `.z64` and pad to 4 bytes itself.

**Test (2026-10-24).** Source: Majora's Mask (USA) from RomM, downloaded through the RomM-ES hook (test 3).
- The file is named `.n64` but its header is `37 80 40 12`, i.e. **v64** (2-byte swapped). The format must be
  detected from the first four bytes (`80 37 12 40` z64, `37 80 40 12` v64, `40 12 37 80` n64), not from the extension.
- Converted to big-endian with a small script (`python -I to_z64.py`, `xxhash` via `uv run --with`): XXH3-64
  `0xEF18B4A9E2386169`, which matches `rom_hash` in Zelda64Recomp `src/main/main.cpp`.
- Copied to `~/.config/Zelda64Recompiled/mm.n64.us.1.0.z64` and started Zelda64Recomp 1.2.2 via `quiver --run`.
  The main menu shows **"Start game"** with no ROM dialog (screenshot); the file was kept, not deleted. Ending the
  game ended `quiver --run` as well. Booting into gameplay was not checked.

**Design conclusions.**
- Manifest kind `librecomp` works as assumed: write `<config>/<game_id>.z64`, big-endian, padded.
- The match needs XXH3-64 of the big-endian ROM, which RomM does not provide (it has CRC/MD5/SHA-1 of the file
  as stored). heimspiel either keeps a table "RomM SHA-1 of the original file → librecomp game" or computes
  XXH3 after download. The SHA-1 of the stored file differs per byte order (v64 here).
- Never place a file with an unverified hash: librecomp deletes it, and if the target is a symlink into a
  cache, only the link goes away. A copy is cheap (32 MiB).

## 5. Ship of Harkinian 9.3.1 (Dewey Bravo)

**Code** (`soh/soh/OTRGlobals.cpp`, tag 9.3.1): `RunExtract` takes `argv[1..]` as ROM paths (lines 425-428)
and calls Torch for them (`CallTorch`, lines 614-632). Torch is built in; the AppImage ships no separate
`soh-torch` (contents: `soh.elf`, `soh.o2r`, `assets/`). Once all arguments are processed, the popup
"All files have been processed. Run SoH?" appears (Yes/No, lines 594-609). If `oot.o2r` already exists, SoH
asks "Extract again?" (lines 617-626).

**Test (2026-10-24).** Source: Ocarina of Time (USA) (Rev B) from RomM via the RomM-ES hook; again a `.n64` file
with a v64 header (`37 80 40 12`).
- `./SoH.appimage "<rom>"` (no `~/.local/share/soh` before): the window opens, the extraction runs without
  any interaction (log: `Done! Took 6190ms`) and writes `~/.local/share/soh/oot.o2r` (33.9 MB) plus
  `shipofharkinian.json`, `imgui.ini`, `mods/`. SoH handles the v64 byte order itself. Then the popup
  "Run Ship of Harkinian – All files have been processed. Run SoH?" (Yes/No) appears and waits (screenshot).
- Terminating that process and starting `./SoH.appimage` without arguments goes straight to the Ocarina of Time
  title screen, with no dialog (screenshot).
- Process names: the AppImage runs as `AppRun`/`SoH.appimage`, the window class is `soh.elf`.

**Design conclusions.**
- Manifest kind `args` works as a separate provisioning step, not as the launch command: run `soh <rom>` once
  (hidden or with a "preparing" notice), wait for `oot.o2r` and `Done!` in the output, end the process, then
  launch normally without arguments. Do not pass the ROM on every launch: with an existing `oot.o2r`
  SoH asks "Extract again?".
- `oot.o2r` lives in the user data dir (`~/.local/share/soh/`), not next to the AppImage; it must be recreated
  after SoH updates that change the archive version (`OTRGlobals.cpp:418-475`).
- No ROM conversion is needed for HarbourMasters ports.

## 6. ps4-pkg-tool

Release `v20260801-153821-45baedaa`, `ps4-pkg-tools-Linux.tar.gz` containing `ps4-pkg-tool` and
`ps4-pkg-tool-gui`. Usage: `ps4-pkg-tool <path/to/pkg> [path/to/output]` or
`ps4-pkg-tool --dir <directory/with/pkgs> [path/to/output]`.

**Port chosen.** God of War III Remastered with SpartanPort (FelipePrado0/SpartanPort, GPL-2.0, ~4000 stars,
release `windows-v2.7.0` with `spartanport-x86_64.AppImage`). It needs the extracted game folder (`eboot.bin`,
`sce_module`, `sce_sys`), tested with CUSA01623/CUSA01715 01.00/01.02; an update folder can be laid over it.
Launcher settings on Linux: `~/.config/spartanport-launcher` (`settings.json`); the README mentions `--play`
with saved settings (not checked with the AppImage). awesome-decomp-games lists about 20 PS4 ports (Bloodborne,
Uncharted NDC, Shadow of the Colossus, inFAMOUS Second Son, The Last Guardian, …); only a few ship Linux builds.

**Original.** The user's own disc image `GodOfWar3.iso` (43 GB, ISO 9660/UDF volume `PS4VOLUME`):
`app/CUSA01623/app.pkg` (39.5 GB), `PS4/UPDATE/PS4UPDATE.PUP`, `license/rif.`, `bd/param.sfo`. udisks mounted it
read-only without root (`/run/media/<user>/PS4VOLUME`).

**Test (2026-10-24).**
- The first 64 MB of `app.pkg`: header recognised (`\x7fCNT`, content ID `UP9000-CUSA01623_00-0000GODOFWAR3PS4`),
  then `Extraction failed: PKG file size is different` (expected for a truncated file).
- The full `app.pkg` from the mounted image: `Segmentation fault (core dumped)` after 0.6 s. Before that the
  tool wrote only the unencrypted metadata entries into `CUSA01623/sce_sys/` (35 files, 19 MB: `param.sfo`,
  `license.dat`, `entry_keys`, `image_key`, `playgo-*`, `pic1.png`, …), no `eboot.bin`, no `sce_module`, no game
  data. The partial folder was deleted afterwards.
- Most likely cause: the game data (PFS image) of a retail PKG is encrypted with keys that only a console
  can derive. We did not prove that this is what makes the tool crash.

**Quiver and SpartanPort.** `quiver --download SpartanPort` (entry with `releaseAssetFilter`
`spartanport-x86_64.AppImage`) fails twice with "No eligible download was found." although `--list` shows
`Latest: vwindows-v2.7.0` and the GitHub API was not rate-limited. That message is the CLI fallback when no
release object is available (`CLIHandler.cs:626-628`, `GameDownloadService.cs:27-33`). SpartanPort uses
platform-prefixed tags (`windows-v…`, `macos-v…`) and is a verified entry in Quiver's own catalog; root cause not
pinned down.

**Design conclusions.**
- The assumption "PS4 original as PKG → `ps4-pkg-tool` → folder" does **not** hold for retail discs or retail
  PKGs, which is what owners usually have. The tool can only help with already decrypted (fake) PKGs.
- PS4 ports therefore need a decrypted folder dump made on the user's own (jailbroken) console. heimspiel cannot
  create it. Manifest kind `dump`: heimspiel checks the folder (`eboot.bin`, `sce_sys/param.sfo` with the
  expected title ID and version), links it to the port, and otherwise explains what is missing.
- heimspiel can still read title ID and version from `param.sfo` in a disc image or PKG header without
  decrypting, so it can show "you own God of War III (CUSA01623), the port needs a decrypted dump".
- Quiver cannot install every repo from the CLI (SpartanPort). heimspiel needs a fallback: download the
  release asset itself (same `releaseAssetFilter` logic) or report it upstream.

## Side findings: package formats on the target system

- **Flatpak is missing** on this Omarchy system. The decision "emulators via Flatpak" forces the wizard into a
  system change here (pacman + runtimes). On SteamOS, Bazzite and Fedora Flatpak is already present. Open
  question for the wizard: AppImage as an equal path where emulators ship one.
- **Heroic** ships as AppImage (x86_64 and arm64 in the GitHub release), Flatpak and AUR. heimspiel must look
  for its configuration in both places: `~/.config/heroic/` and `~/.var/app/com.heroicgameslauncher.hgl/config/heroic/`.
- **AppManager** (AppImage manager, in use here) stores AppImages *without extension* in `~/Applications/`
  (`~/Applications/WowUp`) and writes `.desktop` files for them. Consequences:
  - ES-DE does not find emulators installed this way, because `es_find_rules.xml` expects names with the
    extension (`~/Applications/RetroArch-Linux*.AppImage`, line 17). heimspiel finds emulators itself and
    writes the found path explicitly instead of relying on the find rules.
  - Quiver under `~/Applications` would put its library (`apps.json`, `Apps/`, `Cache/`, `Backups/`) there.
    heimspiel runs Quiver in its own folder or sets `AppsPath`.
  - The source "manual PC games" from `.desktop` files needs an exclusion list, otherwise tools such as WowUp
    or AppManager itself end up in ES-DE.

## 7. Tauri 2 on NVIDIA/Hyprland

**Setup.** Minimal Tauri 2 project without a Node frontend (`frontendDist` = static HTML with a CSS animation
and a WebGL query), system Rust 1.98.1, `webkit2gtk-4.1` 2.54.1 already installed. `cargo build` (dev) took
59 s without errors.

**Observations** (`target/debug/tauri-hello`, each run for 6–7 s):

| Environment | Result |
|---|---|
| no variable | exits immediately: `Gdk-Message: Error 71 (Protocol error) dispatching to Wayland display.` (twice) |
| `WEBKIT_DISABLE_DMABUF_RENDERER=1` | runs; text, CSS animation and WebGL visible (screenshot), about 200 MB RSS |
| `__NV_DISABLE_EXPLICIT_SYNC=1` | runs, no messages |
| `GDK_BACKEND=x11` (XWayland) | runs, but `Failed to create GBM buffer of size 900x600: Invalid argument` |
| `WEBKIT_DISABLE_COMPOSITING_MODE=1` | crashes like with no variable |

**Design conclusions.**
- Tauri stays. Without a countermeasure, though, the app does not start at all on NVIDIA under Wayland, so this
  is mandatory, not polish. (The desktop view moved to Spieli, so this now concerns the setup wizard.)
- At startup, before GTK initialises (first line of `main`), the app sets an environment variable when it
  detects Linux, Wayland and the NVIDIA driver (`/proc/driver/nvidia/version`) and the user has not set one.
  `__NV_DISABLE_EXPLICIT_SYNC=1` is the candidate default because it keeps the DMABUF renderer;
  `WEBKIT_DISABLE_DMABUF_RENDERER=1` is the fallback if it causes problems. Both can be overridden by a
  setting/variable.
- Still to check on KDE/GNOME with NVIDIA; the failure sits in the driver/WebKit path, not in the compositor,
  so it probably affects all Wayland sessions.
